# Coach 2: Training Plan Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A structured training plan in pace: sessions and blocks in a local file, pushed to Garmin one session at a time (or in batches), and compared against what was actually done.

**Architecture:** `pace/plan.py` is the plan model on top of `pace/store.py` (coach plan 1).
`pace/sports.py` maps Garmin activity type keys to sport families.
`pace/planpush.py` turns sessions into Garmin writes through the existing `run_write`, and `pace/matching.py` is a pure matcher of sessions to activities.
`pace/commands/plan.py` wraps everything in the envelope; `workout calendar` is a new read in `pace/commands/workout.py`.

**Tech Stack:** Python 3.14, typer, garminconnect (via `pace.api.safe_call`), pytest + typer `CliRunner` with `safe_call` monkeypatched (pattern: `tests/test_workout_cmd.py` `fake_api`).

**Spec:** `docs/superpowers/specs/2026-11-17-coach-plan-design.md` section 2 (Plan), Constraints, Anti-goals (drift).
Plan 2 of 4; depends on plan 1 (`pace.store`, `pace.diary`).

## Global Constraints

- Every write contract of the 2026-09-04 spec section 7 holds: one envelope, `--dry-run` on every Garmin write showing the exact payloads, writes never read the cache, success invalidates `get_workouts:`; Garmin writes go through `pace.writes.run_write`.
- Plan file `$PACE_HOME/plan.json`; archive dir `$PACE_HOME/plans/`; locked read-modify-write via `pace.store.locked`; corrupt file -> `internal` with path hint, never overwritten.
- Session `sport`: `running | cycling | swimming | walking | hiking | strength | mobility | other`; only the first five can carry a `workout` and be pushed.
- Session `intensity`: `rest | easy | moderate | hard`.
- Stored `status`: `planned | pushed | skipped`; `done | missed | modified` are derived only.
- Pushed workout names are prefixed exactly `"pace: "`.
- `modified` threshold: actual duration or distance differs from the target by more than 20 % (`MODIFIED_TOLERANCE = 0.20`, stated in `pace schema`).
- Deleting a workout on Garmin removes its schedules (verified 2026-11-17); a 404 on delete means "already gone" and counts as success.
- Weeks and days are local dates; "today or later" uses `date.today()`, injectable as `today` in pure functions for tests.
- No real Garmin ids in tests or docs (synthetic ids only).
- ASCII only; markdown one sentence per line; pytest and ruff clean at every commit; no Claude attribution.

## Review Focus

1. A batch push where the second session fails (rate limit, Garmin rejection): the first stays pushed and recorded, the second reports its error, the envelope says which is which, and re-running the same command does not duplicate the first. Test in Task 3.
2. A session pushed, then its date changed, then pushed again: exactly one Garmin workout exists afterwards (old deleted first), and the plan holds the new ids. Test in Task 3.
3. A workout upload that succeeds but whose schedule call fails: the plan records the uploaded `workout_id` so the next push deletes it instead of leaving an orphan. Test in Task 3.
4. Two runs on one day (double day, or a run plus a planned run moved from yesterday): matching is one-to-one, closest target duration wins, the other activity is `unplanned`. Test in Task 4.
5. A session edited in the Garmin app (deleted there) and then unpushed by pace: the 404 is success, the session returns to `planned`. Test in Task 3.

def archive_dir() -> Path

### Task 3: Push and unpush

**Files:**
- Create: `pace/planpush.py`
- Modify: `pace/commands/plan.py`, `pace/commands/schema.py`, `docs/CONTRACT.md`
- Test: `tests/test_planpush.py`

**Interfaces:**
- Consumes: Task 1-2; `pace.workout.build_workout`; `pace.writes.WriteSpec/run_write`; the paths and bodies used by `workout push/schedule/delete` in `pace/commands/workout.py` (upload `upload_workout(payload)`, schedule `connectapi("/workout-service/schedule/{id}", method="POST", json={"date": iso})`, delete `connectapi("/workout-service/workout/{id}", method="DELETE")`).
  Extract three spec builders from `pace/commands/workout.py` into `pace/workout.py` so both callers share them: `upload_spec(dsl) -> WriteSpec`, `schedule_spec(workout_id, iso) -> WriteSpec`, `delete_spec(workout_id) -> WriteSpec`; `workout push/schedule/delete` then call them (behavior and tests unchanged).
- Produces (`pace.planpush`):

```python
async def push_sessions(ids: list[int], *, dry_run: bool) -> dict
async def unpush_sessions(ids: list[int], *, dry_run: bool) -> dict
```

  Return `{"results": [{"id": int, "ok": bool, "steps": [...], "error": {...} | None, "session": {...}}], "pushed"|"unpushed": n, "failed": n}`; envelope `ok` stays true when at least one session succeeded, and is `false` with the first error when all failed (same rule as range fan-out partial failures).
  Per session, in this order, each step a `run_write`:
  1. If `garmin.workout_id` is set: delete it (404 counts as done).
  2. Upload the DSL with `name` = `"pace: " + workout.name` (if the DSL name already starts with the prefix, do not double it).
  3. Schedule on the session date.
  After each step that lands, persist the new ids inside a short `plan.transaction()` (reload, update that one session, save): after delete `garmin = None`; after upload `garmin = {"workout_id": id, "schedule_id": None}`; after schedule `schedule_id` set, `status = "pushed"`, `stale = False`.
  The plan file is not locked during network calls.
  Refusals before any call (`bad_args` for that session, others proceed): unknown id, `skipped` status, sport not PUSHABLE, `workout` None.
  `unpush`: delete `garmin.workout_id` (404 ok), then `garmin = None`, `status = "planned"`, `stale = False`; a session without `garmin` is a no-op success.
  `--dry-run`: no network, no file change; each result lists the exact payloads it would send, with the delete step present when ids exist.

### Task 4: Matching, `plan status`, `workout calendar`

**Files:**
- Create: `pace/matching.py`
- Modify: `pace/commands/plan.py`, `pace/commands/workout.py`, `pace/commands/schema.py`, `docs/CONTRACT.md`, `README.md`
- Test: `tests/test_matching.py`, `tests/test_plan_cmd.py`, `tests/test_workout_cmd.py`

**Interfaces:**
- Consumes: Task 1 (`sessions_in`, `family`), `cached_call("get_activities_by_date", from, to, None, ...)` as in `activity list`, `with_effort` is NOT applied (list rows carry no RPE).
- Produces (`pace.matching`):

```python
MODIFIED_TOLERANCE = 0.20
def match(sessions: list[dict], activities: list[dict], *, today: date) -> dict
```

  Activities are Garmin list rows (`activityId`, `activityType` as dict or flattened key, `startTimeLocal`, `duration`, `movingDuration`, `distance`, `elevationGain`, `averageSpeed`, `averageHR`).
  Algorithm:
  1. Sessions with a manual `activity_id` take that activity (if present in the range) first.
  2. Remaining sessions grouped by (date, sport); for each group, candidate activities on the same local date (`startTimeLocal[:10]`) with `family(type) == sport`; assign greedily by smallest `abs(activity duration - target.duration_s)` (sessions without a duration target sort after those with one, then by id); each activity at most once.
  3. Classify each session: matched -> `modified` if any of duration/distance has a non-null target and `abs(actual - target) / target > MODIFIED_TOLERANCE`, else `done`; unmatched -> `skipped` if stored skipped, `missed` if date < today, else stored status (`planned`/`pushed`).
  4. Unmatched activities -> `unplanned`.
  Output: `{"days": [{"date", "sessions": [{"id", "title", "sport", "status", "target", "actual": {"activity_id", "duration_s", "distance_m", "elevation_m", "avg_pace_s_per_km", "avg_hr"} | None, "stale"}], "unplanned": [{"activity_id", "sport", "duration_s", "distance_m"}]}], "totals": {sport: {"planned": {"duration_s", "distance_m"}, "actual": {...}}}, "intensity_planned_s": {intensity: seconds}}`.
  Days without sessions or activities are omitted.
  `actual.duration_s` uses `movingDuration` when present, else `duration`.

- `plan status [--from] [--to] [--days]`: default today-7 .. today+7; activities fetched for `from .. min(to, today)`; `cache` report from the fetch.
- `workout calendar [--from] [--to] [--days]`: months covering the range via `connectapi("/calendar-service/year/{Y}/month/{M0}")` (M0 = month - 1) through `cached_call` with TTL 300; returns items with `itemType == "workout"` in range, as `{"date", "schedule_id": id, "workout_id": workoutId, "title"}` sorted by date; at most 12 months per call (`bad_args` beyond).
